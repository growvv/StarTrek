# Themis 崩溃检测实验：现状与结论

> 2026-11-19。记录这一轮按 FuncDroid 论文的数据集做 bug 检测实验的结果。
> 本文只写实际测到的事实，不写期望。

## 0. 一句话结论

方法与判定链路已完整实现并验证；**尚未检测到任何一个已知 bug**。阻塞点是
executor 能力与环境适配，不是判定逻辑。

## 1. 数据集

来源：FuncDroid 论文的 Themis 基准（`daxiami233/FuncDroid` 仓库的
`Effectiveness evaluation`）。数据集提供每个版本的真实崩溃 logcat、
FuncDroid 建的功能图与运行日志，**不提供 APK**。

| 项 | 实测 |
|---|---|
| app 数 | **13**（论文称 20，其中 7 个的仓库已下线） |
| 版本数 | 22 |
| 独立崩溃签名 | 28 |
| 可推导出触发任务 | 13/22 |
| 已下载 APK | 11 |
| 已映射源码仓库 | 12 |

论文目标里的「至少 20 个 app」**无法达成**：数据集本身只有 13 个可用。

## 2. 判定口径

与 FuncDroid 的检测器一致：

- `FATAL EXCEPTION` 且 `Process:` 指向目标包；
- 异常类型与栈顶应用帧都要匹配；
- 一个版本记录的**全部**崩溃都要出现，否则不算命中。

验证：22 个版本各自用数据集里的日志做自匹配，**22/22 通过**。跨版本误报从 2
降到 1，剩下那一个是数据本身的包含关系（AnkiDroid 2.7beta1 的日志确实包含
2.9alpha4 的全部崩溃），不是匹配器缺陷。

## 3. 任务推导

数据集给的是 `function_description`（页面描述），不是可执行任务。直接把它交给
agent 会让它「看一眼菜单」，永远到不了崩溃代码。

`bug_task.py` 从崩溃栈反推触发动作（`DeleteTask` → 删除文件、`CardBrowser` →
打开卡片浏览），覆盖 13/22 版本。其余 9 个只有平台帧，无法推导，如实报告为
「不可推导」而不是编造任务。

## 4. 实验执行器

`bug_experiment.py` 的完整链路：

1. 卸载旧版 → 安装数据集指定的精确版本（降级会被包管理器拒绝）；
2. 授予该版本声明的存储权限（2018 年的 app 用 `READ/WRITE_EXTERNAL_STORAGE`，
   2021 年后用 `MANAGE_EXTERNAL_STORAGE`，两者都要）；
3. 播种任务需要的数据（Markor 读 `/storage/emulated/0/Documents/markor`，
   不是名为 `Notebook` 的目录）；
4. 清除首次启动对话框（Licenses 通知、权限弹窗）；
5. 交给 agent 执行，读回 logcat 判定。

## 5. 实测结果

| 版本 | 结果 | 失败原因 |
|---|---|---|
| Amaze 3.3.2 | 未检出 | agent 点了 Delete 并确认，但崩溃需要「删除空列表项」的状态 |
| AnkiDroid 2.6beta6 | 未检出 | 步数耗尽 |
| AnkiDroid 2.7beta1 | 未检出 | 步数耗尽（6 步） |
| AnkiDroid 2.9 / 2.9.1 | 未检出 | 曾卡在权限对话框，修复后仍未走到目标 |
| collect 1.23.0 | 未检出 | 步数耗尽 |
| markor 0.3.9 | 未检出 | agent 在导航菜单里循环，未使用文件列表 |

**6 个可运行版本，0 检出。**

## 6. 已修复的真实缺陷

| 缺陷 | 影响 | 修复 |
|---|---|---|
| `#N` 被当作版本号 | APK 查找全部失败 | 改用目录名里的版本名 |
| 下载文件名用版本码 | 同 app 多版本互相覆盖，10 次「成功」只剩 3 个文件 | 改用版本名命名 |
| 旧版本不在 GitHub Releases | 6/13 无法运行 | 增加 F-Droid 归档作为第二源 |
| 首次启动对话框 | Markor agent 1 步就宣布完成 | 实验器预处理对话框 |
| 对话框内窗口焦点不变 | 误判「已就绪」 | 改为读 UI 内容 |
| 存储权限机制因年代而异 | 文件列表显示为空 | 两种机制都授予 |
| 播种目录猜错 | 同上 | 从 app 的 shared_prefs 读出真实路径 |
| 判定接受部分崩溃 | 一个版本可顶替另一个 | 要求全部崩溃出现 |

## 7. 阻塞点

**executor 能力不足**（主要）。当前 `mobile_agent` 是单循环 agent，每步一次
模型调用，没有分层规划。它在 20 步内完不成「选中文件 → 打开信息对话框」这类
多步操作，会退化成在导航菜单里来回点击。

**数据集规模**（不可解）。13 个 app 是硬上限。

**机器资源**。125G 内存里可支配约 10–16G，四路并行会耗尽 swap；实测只剩
1–2 个模拟器可用。

## 8. 本轮对 executor 的改进

**agent 第一次走到了崩溃入口。** 修好 `tap` 的 content-desc 支持与长按能力后，
markor 0.3.9 的一次运行里全部动作都成功：第 1 步长按文件、第 12 步点开
`Info`，最终界面确实是 `FileInfoDialog`（Name / Location / Size / Text Lines
全部渲染）。这是本轮第一次让 agent 抵达数据集标注的崩溃点。

但它没有崩溃，因为该 bug 需要 `FileUtils.isTextFile` 收到空扩展名（NPE 在
`String.startsWith` 的 null 接收者上），而列表里的文件都带 `.md`/`.txt`。
无扩展名的文件不被文件浏览器列出，目录又不支持长按菜单——具体触发条件尚未
还原出来。这属于任务推导的精度问题：`bug_task` 给出「打开文件信息对话框」，
但真正需要的可能是「对某个无扩展名的项打开信息」。

另外，日志里出现的 11 条 `FATAL EXCEPTION` 全部来自 **uiautomator 自身**
（`UiAutomationService already registered`），判定的 `Process:` 过滤把它们正确
排除了——这正好验证了「只认目标进程」这条规则的必要性。

## 8.1 屏幕身份与安装对话框

**屏幕身份**（`mobile_agent/screen.py`）。Markor 的失败看得最清楚：agent
的 plan 是对的（「点 overflow，选 Info」），但第一次点击打开了编辑器，随后
十四步都在编辑器的 overflow 里找 Info。它从未意识到界面变了。

现在 observation 会说明「当前屏幕是什么」以及「上一个动作有没有改变它」，
系统提示也要求它在界面变化后重新读屏。实测效果：agent 的思考里出现了
「I'm still in the file editor」——第一次表现出它知道自己在哪。仍没走到
对话框，但缺口从不可见变成可见。

**安装/权限对话框**。AnkiDroid 2.7beta1 在 API 28 上会先弹 packageinstaller
的 ALLOW 对话框，之前被误判为「卡住」。已加入可清除列表。

## 8.2 确认对话框守卫

Amaze 的一次运行里，agent 长按文件、点 Delete、弹出「Delete items permanently?」
之后就宣布完成——文件从没被删除，而运行记录写的是「已删除」。

现在：界面上还有带确认按钮的对话框时，第一次 `done` 会被拒绝并给出理由；
agent 可以第二次坚持（如果那个对话框就是目标，不会被困住）。两种按钮词表都识别：
平台的 `android:id/button1` 与 Material 的 `md_buttonDefaultPositive`（Amaze 用后者，
也是第一次漏掉的那个）。

修好之后同一条运行走到了真正删除：目录变为 `0 folders and 0 files`。但仍然没崩溃——
3.3.2 的 `onPostExecute` 在这里处理了空列表。数据集记录的 `Index: 0, Size: 0`
需要的状态还没还原，可能是「删除动作一个文件都没删掉」的情形（删除列表为空），
而不是「删完之后目录为空」。

## 9. 仍未解决的交互障碍

在 API 28 上手动复现 AnkiDroid 的崩溃时遇到的具体问题：

- 空 deck 里没有卡片，`0 cards due`，点 deck 不会进入复习界面；
- 用 UI 添加卡片时，`uiautomator dump` 在键盘弹出时返回
  `null root node`，字段填充不可靠；
- Markor 0.3.9 的 File Info 不在列表页 overflow 里，长按也进的是编辑器。

这些都是**真实的 UI 交互复杂度**，不是代码缺陷。它们解释了为什么一个
单循环 agent 在 20 步内做不完，也解释了为什么 FuncDroid 需要自己的多 agent
框架（规划 + 执行 + 反思 + 记忆）。

## 10. 结论与建议

**本轮能确认的**：方法链路完整、判定严格、7 个会导致实验无效的缺陷已修复、
数据集与 APK 供应链打通。

**本轮不能确认的**：方法能否发现 bug——因为 executor 不足以走到崩溃点。

要继续，必须换 executor：

- 分层规划（先定子目标，再逐步执行）；
- 每步显式的界面状态机，而不是每步重新看屏幕；
- 更长的步数预算与失败重规划；
- 或直接接入 GUI-Owl 专用模型（本机有 `GUI_Owl_7B`，未启用工具调用）。

在这之前，任何检测率数字都反映 agent 的能力，而不是方法的价值。
