# 功能地图覆盖率：四个 app 的实测结果

> 2026-11-19。分母来自各 app 的**源码资源**（`res/menu/*.xml`、`res/navigation/*`），
> 不是被比较工具的功能列表。

## 结果

| app | 覆盖 | 说明 |
|---|---|---|
| activitydiary | 15/15 = 100% | |
| amaze | 19/20 = 95% | 缺 `delete`：该轨迹的确认按钮标签与本机 locale 不符，未采到 |
| markor | 17/17 = 100% | |
| omninotes | 23/23 = 100% | |

**平均 98.8%**，四个 app 全部达到 90% 以上。

明细见 `runs/coverage-report.json`。

## 这里的分母是什么

`benchmark/coverage/<app>.yaml` 是手写的功能清单，每一项都指向 app 源码里的
证据（`source: res/menu/filesystem__menu.xml#rename`）和它在界面上留下的痕迹
（`ui_evidence: [重命名, Rename]`）。这把「这个 app 能做什么」定义在**被测工具
之外**，所以覆盖率衡量的是我们的图，不是我们和 FuncDroid 命名的一致程度。

对照：FuncDroid 数据集自带的 `fdg.json` 是**被比较工具自己建的功能图**
（34 个 build、3200 个功能）。它只能用作规模参考，不能当分母——`function_inventory.py`
把这一点写成 `is_answer_key=True`，并在报告里带出来。

## 本轮为达到该覆盖率修掉的问题

| 问题 | 症状 | 影响 |
|---|---|---|
| `tap` 不支持 `content-desc` | 只有图标的控件（overflow 菜单、NEXT、搜索）看得到点不到 | 整类动作不可能完成 |
| agent 无长按能力 | Markor 的文件操作全在长按菜单里 | 重命名/详情/删除不可达 |
| 轨迹无法声明功能名 | 模型按看到的界面命名（QuickNote 打开 → `open_main_tab`） | 已采到的功能被判为缺失 |
| 轨迹摘要不含声明的名字 | 改名后仍报「已处理」 | 静默保留模型的旧命名 |
| 单步轨迹走 fallback 分支时丢失名字 | `open_quicknote` 仍是 `activate_tab` | 同上 |
| 失败轨迹仍产出卡片 | 3 步全失败的轨迹生成了 `write_quick_note` | 图虚报覆盖 |

最后一条让 markor 的覆盖率从虚高的 88% 降到诚实的 82%，再加上真实补采的两条
轨迹（`open_quicknote`、`file_details`）与全部声明的名字，才到达 100%。中间那个
更低的数字才是可信的。

## 尚未达成

目标是「至少 20 个 app」。当前只有 4 个，原因是每个 app 都需要：

1. 一份从源码整理的功能清单（手写，约 15–25 项）；
2. 一组脚本化轨迹（每条一个功能，需要知道该 app 的界面路径）；
3. 在设备上逐条采集。

前两项可以部分自动化，第三项受限于脚本轨迹必须逐条验证。其余 16 个 app
的清单与轨迹尚未建立；按本轮 markor 的经验，单个 app 从 80% 到 95% 需要
1–2 小时的真实设备操作。
