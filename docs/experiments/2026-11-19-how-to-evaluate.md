# 如何评估这个方法

> 2026-11-19。回答一个问题：在「比 FuncDroid 检出更多 bug」这条路走不通之后，
> 应该怎样评估这套方法。

## 1. 先把两个主张分开

这套工作实际上包含两个可以独立成立的主张：

| | 主张 | 现在的状态 |
|---|---|---|
| **A** | 能从轨迹建出覆盖 app 功能的功能图 | **已成立**。4 个 app 在源码清单上平均 98.8%，三个 100% |
| **B** | 这张图能帮 agent 完成 / 发现更多东西 | **未测出**。所有下游实验两臂都贴在地板上 |

把 A 和 B 混在一起谈，是这一轮反复受挫的根源。A 是**构造性**主张，只要图和
清单对得上就成立，不需要跑 agent。B 是**因果**主张，需要对照实验，而且对
执行器能力极其敏感。

## 2. 为什么「检出更多 bug」这条路走不通

三个独立的理由，任何一个都足以让它失败：

**天花板。** FuncDroid 报告 20 个 app、62 个 bug。数据集里可用的只有 13 个
app、22 个版本，其中 6 个能真正启动。即使检出率 100%，上限是 13，达不到 62。
这不是努力能补的，是数据规模决定的。

**地板效应。** 崩溃是**下游、高方差**的事件：agent 必须走完整条路径，**并且**
恰好落在触发 bug 的那个状态上。当前执行器走不完全程，于是两臂都是 0，
差值没有意义。此时无论方法好坏，测出来都是 0。

**单位错位。** 方法的作用机制发生在**更近的地方**——描述有没有把 agent 引到
正确的界面。用它去预测「是否恰好崩溃」，中间隔了太多与描述无关的因素
（源码考古、前置状态、时序）。

## 3. 正确的对照是什么

这套方法声称的是：

> 契约式描述比用户原始 goal 更能把 agent 带到目标状态

那么：

- **对照必须是 raw goal**，不是 FuncDroid。FuncDroid 是另一个系统，和它比
  检出数混合了太多变量。
- **结果必须是中间量**（是否到达目标界面），不是是否崩溃。
- **两臂都必须有合理的成功率**，否则测的是地板，不是方法。

## 4. 四个可行的评估设计

### A. 可达性（已实现，推荐作为主实验）

把目标从「让 app 崩溃」换成「让崩溃代码所在的那个界面出现在屏幕上」。
判定直接从 UI dump 读：`FileInfoDialog` 的控件 id 出现即算到达；删除确认框的
正按钮出现即算到达。

**为什么这是对的**：它不需要崩溃发生，不需要读 app 源码还原前置条件，而且
**正好落在方法声称的位置**——描述的任务就是把 agent 引到正确的界面。

**成本**：已实现（`specfcg/benchmark/reachability.py`、`reach_experiment.py`、
`scripts/run_reach_experiment.py`），单版本约 5 分钟。

**局限**：到达界面不等于触发 bug。它测的是「必要条件」，不是「充分条件」。
但对一个方法主张来说，必要条件被证伪比充分条件更有信息量。

### B. 配对消融（扩样本）

graph 描述 vs raw goal，同一批任务，记录 steps-to-goal 与成功率。

**必须做的修正**：现在只有 20 个任务，且两臂都在地板。要把它做成有统计
意义的结论，需要：

- 任务数 ≥ 100（每个 app 20+，选 agent 有合理成功率的任务）；
- 预先排除两臂都必失败的任务（它们只贡献噪声）；
- 报告配对差异的置信区间，不是单个差值。

**成本**：2–3 天，主要花在筛任务上。

### C. 图作为覆盖工具（已基本完成）

同一批 app，你的图 vs FuncDroid 的图，对**源码真值**的覆盖。

这是唯一能直接和 FuncDroid 比较、且完全绕开执行器的维度。

**关键**：分母必须来自源码（`res/menu/*.xml`），不能来自 FuncDroid 的
`fdg.json`——那是被比较工具自己建的图，用它当分母测的是「命名一致度」。

**成本**：每个 app 一份清单，约 1 小时。已完成 4 个。

### D. 失败定位

postcondition 能否指出哪个契约被破坏。

**优点**：不需要 bug，不需要长路径，判定便宜。
**缺点**：它测的是诊断能力，不是建图能力，属于另一个主张。

## 5. 建议的组合

1. **主张 A 用 C 来证明**，把 app 数补到 20。这是工作量，不是风险。
2. **主张 B 用 A 做主实验**，B 作为强化。
3. **如实报告地板效应**：说明当前执行器是限制因素，并给出两臂都到达的样本数。
   这比假装有效强得多，也比只报「0 检出」有信息量——「两臂都到达」本身
   就说明实验设计可行，只是当前版本的触发条件更苛刻。
4. **不要用检出数做 headline**。它是这套方法最弱的一环，而且受数据规模
   硬约束。

## 5.1 一个刚暴露出来的结构问题

现有四张图建自**当前版本**（markor 2.10.9、amaze 当前版），而 Themis 里的被测
build 是**旧版本**（markor 0.3.9、amaze 3.3.2）。用 2024 年的图去规划 2020 年的
build，是一次版本错配：

- 界面控件、导航结构都可能变过（Markor 的 overflow 菜单内容就不一样）；
- 更直接的是**功能未必对得上**：amaze 的图里没有 `delete` 卡片，所以 graph 臂
  在「删除文件」这个目标上直接 `no_plan`。

这不是 bug，是测量的边界：**graph 臂的上限由图的覆盖决定**。要做 Themis 上的
配对实验，图必须建自**同一个 build**（在 API 28 模拟器上采集那个版本的轨迹），
否则 graph 臂输在「图里没有这个功能」，而不是输在「描述不好」。

这条必须在任何配对结论旁边写清楚。

## 6. 一个必须承认的事实

如果 A 实验显示**两臂到达率没有差别**，那么这套方法的核心主张在当前执行器上
就是没有被证实的。这不代表方法错了，但意味着：

- 不能声称「契约式描述更好」；
- 能声称的是「能建出高覆盖的图」（A），以及「图能支撑规划」（规划器产出了
  可执行路径）；
- 下一步应该是找一个更强的执行器重做 A，而不是继续调环境。

诚实地划出这条线，比任何数字都重要。
