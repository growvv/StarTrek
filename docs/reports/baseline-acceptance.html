7. 方案评估：好的地方与风险

结论：方案方向是对的，但验收只完成了“能跑”，还没完成“效果”。 学术开源基座 + 最小 wrapper + 最终态判分 + 真机证据，这四点都已经落地； 但 AgentProg 还没有跑出任何一个完整任务的最终判分，所以现在不能回答 “成功率是多少、是否接近 90%”。

做得好的地方

  • 可对照、可修改：AgentProg 的 STP/WPC/代码生成/视觉定位都在开源代码里， 后续加探索与功能图有明确挂载点。
  • 没有重复造轮子：规划与执行全部用上游实现；wrapper 只做设备环境、日志和判分。
  • 证据可审计：每一步都有真机截图、动作时间、模型原始请求/响应与耗时。
  • 判分不看过程：只看最终屏幕是否满足目标，避免“路径不同就判失败”。
  • 环境问题已工程化：首次引导、通知权限、输入法、APP 启动 Activity 都已自动处理。

风险与不够好的地方

  • 速度慢：gpt-6.1-sol 下每步约 1.5–3 分钟；一个 6–8 步任务要 15–25 分钟， 8 任务全量要好几个小时。
  • 成功率未知：AppAgent 对照只有 2/8；AgentProg 尚无完整数字。 距离你期望的 90% 还有明显差距，必须先补基线数字。
  • 字面步骤会卡住 WPC：标签任务已证明，STP 若把“用工具栏动作”写死， 即使 Agent 已经用 #urgent 达成目标，WPC 仍会 hold。目标措辞必须贴合 APP 语义。
  • 外部中断：Phase A 被低内存回收器停过一次；本次又按你的要求暂停。 两次都不是 Agent 失败，但导致没有完整判分。
  • 任务集仍偏 OmniNotes：8 个任务里 6 个是 OmniNotes， Activity Diary / Tasks.org 各 1 个；跨 APP 覆盖还不够。
