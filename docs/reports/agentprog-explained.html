Why AgentProg

长程任务的瓶颈不是“会不会点”，而是“记不记得住”

论文把 GUI agent 的交互历史重新看成一个程序：变量保存关键信息，控制流决定哪些历史仍然相关。于是“保留什么、丢弃什么”不再靠启发式摘要，而是由程序结构决定。

① 缺乏整体规划

现有 agent 容易完成前两个子任务就以为全部完成；STP 在开始执行前就把任务拆成可检查的步骤和循环。

② 关键信息丢失

上下文压缩把 50 步前记下的电话号码压没了；STP 用显式变量把关键数据“钉”在上下文里。

③ 动态环境 / 部分可观测

弹窗、误触、应用崩溃会让 agent 在错误前提上继续操作；全局信念状态持续做 Predict–Verify–Align。

论文原话：现有方法在 “MarkorTodoList” 任务里只完成了前两项就提前终止；在迭代任务中还会因为记不住最初打开的笔记内容而传错参数。
— arXiv 2512.10371 §2.3 Motivation and Challenges

Method

两阶段、双模式、一棵执行树

先把任务生成 STP（workflow.ap），再由运行时解释器逐行执行。执行器不是照本宣科，而是在“生成动作”和“更新程序计数器”之间交替。

1STP 生成自然语言任务 → 带变量/循环/分支的程序（workflow.ap）
2Action Generation当前步骤 + 截图 + 变量 → 一段 Python GUI 动作
3PC Update根据执行结果决定 hold / continue / break / return
4Belief StatePredict–Verify–Align，发现“以为在表单、其实回了桌面”就恢复

Program-Guided Context Management

执行树裁剪：顺序节点挂到上一个节点下；只保留“未走的分支”与“已完成的循环迭代”之外的活动路径。
同一步骤检索：循环回到同一个 step ID 时，把该步骤过去几次的执行结果注入上下文。
数据流持久化：STP 生成阶段声明的变量是锚点，不会被裁剪掉。

Global Belief State

论文用 Belief MDP 的视角维护“当前环境假设”：我在哪个页面、哪些字段已填、剪贴板/返回栈里有什么。每个低层动作执行后都用新截图校验；一旦观察与假设冲突，就标记 Context Lost 并进入恢复流程，而不是继续点一个已经不存在的 Save。

Start a line with the `#` symbol to indicate that the line is a comment. Comments are used to explain code, and the system will ignore them during execution.

*   **Declaring (Recording) Variables**: Usually done using `record as {variable_name}` or similar natural language phrasing.
