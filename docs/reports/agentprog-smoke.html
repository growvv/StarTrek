1. 为什么用 AgentProg 作为 baseline

要求是“学术界论文里用的、代码开源的 Agent，后续可以改、可以看实现”。 AgentProg 来自清华 AIR（Tsinghua AIR），论文 arXiv 2512.10371（2025-12）， 代码在 github.com/MobileLLM/AgentProg，是面向长程 GUI 任务的 program-guided context management 工作；它用 Semantic Task Program（STP）把执行过程 表示成带变量和控制流的程序，从而在长任务中裁掉无关历史、保留关键数据。 它支持真实 Android（adb），动作覆盖 click / long_press / type / scroll / open_app / drag / press_home / press_back 等。

旧规则要求最终截图同时显示完整目标的过程证据，对“归档/删除/完成”类任务天然不可能， 导致 AppAgent 在 8 个任务上只有 2/8（旧严格规则）。

6. AgentProg 架构（来自源码）



AgentProg 的核心是 Semantic Task Program (STP)：模型先把任务写成一段带自然语言步骤、
条件和循环的程序（workflow.ap），执行器再把当前程序行翻译成 Python GUI 动作。
每一步有两个模型阶段：



    
  
  • Code Generation：给定当前程序行、变量、屏幕描述和 belief state，生成一段可执行 Python
      （例如 mobile.click(view_description=...)、time.sleep(3)）。
    • 
  
  • Workflow Status Update：根据执行结果决定程序计数器（WPC）是继续、跳过、跳出循环还是暂停修复。
    • 




上下文管理由执行树完成：已完成的分支、循环迭代和函数调用细节会被裁剪，变量通过 STP 的显式声明持久化；
belief state 维护“隐藏 UI 状态”的假设并在运行时校验。Grounding 使用 UI-TARS 风格的视觉定位：
把当前截图和 “Click on ….” 指令交给定位模型，返回点击坐标，再由 mobile.click 执行。

8. 局限与诚实说明


    
  
  • 每个任务只跑 1 次；真机存在动画、通知、输入法差异，单次结果不等于统计成功率。
    • 
  
  • AgentProg 论文默认使用 Gemini-2.5-Pro 与 Volcengine Ark 的 UI-TARS-1.5；本报告改用本地
      magpie 的 auto/gpt-6.1-sol 作为主模型和 grounding 模型，属于兼容性替换，
      不能直接与论文数字对比。
    • 
  
  • UI-TARS API prompt 增加了一行坐标归一化说明；这是本地 VLM 与 doubao API 坐标约定不一致导致的
      兼容性改动，不属于 AgentProg 原始 prompt。
    • 
  
  • AgentProg 的 text-augmented 截图路径会先用一个描述模型读取真实截图并生成详细画面描述；
      后续 code generation / WPC 调用的 prompt 中，图片占位符没有注册成
      Prompt.images，日志显示为本地图片路径，模型依赖上一步的详细文本描述。
      UI-TARS grounding 始终使用真实截图。本报告未修改这一上游行为。
    • 
  
  • 最终状态判定依赖外部 VLM（auto/gpt-6.1-sol），可能存在视觉误读；报告同时保留
      确定性文本检查和原始截图，便于人工复核。
    • 
  
  • 没有读取 App 的 SQLite/SharedPreferences 等隐藏状态，只按用户可见的最终界面判定。
    • 
  
  • AppAgent 的新规则分数是对旧最终截图的离线重判，不是重跑；旧严格结果仍保留在
      runs/appagent/。
