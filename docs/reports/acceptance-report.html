失败驱动修补：create_note 从 5 步变成 6 步

第一次运行 5/5 动作成功，但 postcondition 准确判失败：只按一次 Back 仅关闭键盘，仍停在编辑器。 修补后的卡片把最后一个动作拆成两个物理动作：

5. Press the system Back key once to dismiss the on-screen keyboard or clear EditText focus while remaining on the note editor.
6. Press the system Back key a second time to exit the note editor, commit/save the note, and return to the notes list screen.

重跑同一目标：6/6 动作成功，postcondition satisfied=true， goal achieved=true。这是“失败 → 卡片补丁 → 重跑”的完整闭环。

LLM 输出结构审计（针对“字段不要超过 10 个”）

所有要求 JSON 的调用都已压缩为浅层结构；Markdown 卡片固定 7 段。 没有嵌套超过两层的对象，也没有为“解释”单独增加字段。

模型输出字段规模结构说明
Function Card (Markdown)7 个固定章节Intent / Inputs / Preconditions / Postconditions / Effects / Steps / Evidence无 JSON 嵌套
Trace 分段4 字段/对象start, end, name, intent仍 < 10
语义边4–5 字段/边from, to, type, description（可选 evidence）模型可省略 evidence
批量分类 + 计划2 个顶层字段cards（每项 3 字段）；plan（每项 2 字段）已删除 reason 字段
参数绑定1 个顶层字段bindings: {name: value}值层次 ≤ 2
步骤编译3 字段/步action, target, args仅非快速路径使用
postcondition2 字段satisfied, reasonreason 为单句
goal2 字段achieved, reasonreason 为单句
最近一轮还把 batch 分类与“有序计划”合并为一次调用：顶层只有 cards 与 plan 两个字段，单卡 3 个字段、单计划项 2 个字段； 原来逐卡的 reason 字段已删除。这样既减少了调用次数，也降低了模型输出不合法的概率。

结论、局限与下一步

可以验收的部分

  • 真实设备 + 真实 LLM 的完整链路已经跑通：trace → 卡片 → 图 → 规划 → 执行 → 检查。
  • 单卡、两卡、三卡目标均成功；成功运行中的动作全部执行完成（34/34）， postcondition 与 goal 均由模型基于真实 UI 判定。失败的那次 archive 运行也是 6/6 动作成功， 失败来自列表渲染时机（F20），不是动作或规划错误。
  • 失败驱动修补有完整闭环：第一次 Back 只关键盘 → 卡片补丁拆成两次 Back → 重跑成功。
  • 复杂任务不再是“更长的脚本”，而是“更多卡片 + 有序计划 + 每步子目标”；四卡结果见上。

仍然存在的限制

  • 延迟：HY4 Free 单次调用常见 1–4 分钟；三卡任务规划 931s，执行 167s。 规划已通过 batch、磁盘缓存和显式目标快速路径压缩，但全量 benchmark 仍需更快模型或更强缓存。
  • 与论文基线的对照：当前是方法可行性验证，不是与 ProphetAgent / FuncDroid 在相同 benchmark 上的对照实验；复杂任务成功只能说明组合链路可用，不能据此声称优于基线。 下一步需要在相同 app / 任务集上统计 completion、action accuracy 与调用成本。
  • 多实例：重复卡片 + PlanStep.instance 已实现并有单测， 但尚未在真机上跑“同一张卡出现两次”的任务。
  • 能力补全：当图中没有可用卡片时，completer 尚未在真机上验证； 目前所有成功任务都落在已有 5 张卡的能力范围内。
  • 状态隔离：重复运行会在列表留下多张同名笔记；pilot 每例前已 pm clear， 正式 benchmark 需要固定此隔离策略。
  • 外部 app：分享面板只验证到“系统 chooser 打开且预览内容正确”， 没有继续选择具体目标 app，避免产生外部副作用。
  • 4 用例 pilot：因宿主内存压力被终止，未产生结果行；按约定没有重跑。 现有结论来自逐条组合实验，而不是那次批量运行。

建议的下一步

  1. 用当前四卡链路再跑一个“两次 create_note + open + share”的多实例任务，验证 subgoal 绑定与 instance postcondition。
  2. 把逐卡参数绑定合并为一次批量绑定（当前四卡任务为此串行付出 4 次 HY4 调用）； 并把执行阶段的多次 postcondition 检查合并为“每卡一次、最后再一次”。
  3. 在 6 个开源 app 上扩展到 20–30 条用户级任务，按 completion / action accuracy / 调用数 / 时延统计。
  4. 补做 capability completion 的真机实验（例如目标需要“删除笔记”但图中无此卡）。
